## 1. Название и организация

- Название системы: **ReleaseDesk** — информационная система сопровождения публикации мобильных приложений в магазинах приложений.
- Организация / подразделение: АО «СимбирСофт» (г. Ульяновск), направление мобильной разработки: проектные команды, которые выпускают мобильные приложения заказчиков, и специалисты по релизам, которые выкладывают сборки в магазины приложений.
- № из таблицы примеров: своя тема (по каркасу ближе всего к № 24–26 «заявка на доступ / лицензию»: сотрудник создаёт, специалист исполняет).

## 2. Главная сущность и справочник

- Главный объект (одна запись процесса): **заявка на публикацию релиза** — одна версия одного мобильного приложения, которую нужно выложить в один магазин приложений (например, «Мобильный банк 3.4.1 — обновление в Google Play»).
- Справочник (вторая таблица, ссылка числом): **магазин приложений** (Google Play, App Store, RuStore, AppGallery).
- Поле-ссылка (как назовёте в JSON/БД): `storeId`.

## 3. Роли и права

| Роль | Создаёт | Назначает | Меняет статус |
|------|---------|-----------|---------------|
| Менеджер проекта | да | да | нет (только отменяет свою заявку в `New`) |
| Релиз-инженер (специалист по публикации) | нет | нет | да, только по своей заявке |
| Руководитель направления мобильной разработки | нет | нет | нет (смотрит сводку) |

Исполнитель не назначает себя сам: назначает менеджер проекта.

## 4. Сценарий в одно предложение

Менеджер проекта создаёт заявку на публикацию релиза приложения в выбранный магазин → назначает релиз-инженера → релиз-инженер переводит заявку в работу (готовит карточку, загружает сборку, отправляет на ревью магазина) и закрывает её, когда версия опубликована.

## 6. Что не входит в семестр

1. Сборка приложения и CI/CD (GitLab CI, Fastlane) — сборку система не делает, только хранит ссылку в описании.
2. Автоматическая загрузка сборки и метаданных в магазины через их API (Google Play Developer API, App Store Connect API, RuStore API).
3. Получение статуса ревью магазина автоматически — статус меняет человек.
4. Хранение скриншотов, иконок и текстов карточки приложения.
5. Уведомления по почте, в Telegram или Mattermost.
6. Мобильный клиент самой системы, отчёты для печати, выгрузка в 1С.

## 7. Запас под ВКР

Не делается в семестре.

1. **Данные / процесс:** справочник приложений заказчиков и история версий; расширенный жизненный цикл с учётом ревью магазина («отправлено на ревью», «отклонено магазином» с причиной отклонения, «поэтапная раскатка» в процентах), с отображением на четыре базовых статуса.
2. **Связи с другими системами:** получение статуса ревью и публикации через App Store Connect API и Google Play Developer API; привязка к сборке из GitLab CI и задаче в Jira.
3. **Масштаб:** одна заявка на релиз сразу в несколько магазинов (подзаявки на каждый магазин), несколько проектных команд и заказчиков с разграничением доступа по проектам, сотни заявок в месяц.
4. **Аналитика:** время от создания заявки до публикации по каждому магазину, доля отклонённых ревью и их причины, сводка для руководителя по проектам и релиз-инженерам за период.

## 8. Чем не копия соседа

Предметная область — выпуск мобильных приложений в магазины, а не ремонт, бронь или обращения: другая организация (ИТ-компания АО «СимбирСофт»), другой главный объект (релиз версии приложения), другой справочник (магазины приложений) и другие роли (менеджер проекта и релиз-инженер). Тема совпадает с темой моей курсовой работы.
